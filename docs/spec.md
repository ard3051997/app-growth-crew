# MCP-GC Interactive Frontend — Product Spec & Design Prompt

---

## Part 1: What Exists Today

The current `journey_map.html` is a **static, self-contained report** (~5000 lines) generated by the Journey Map MCP server. It embeds all data as inline JSON and renders six views:

1. **Journey Map** — Horizontal stage cards (Onboarding → Dashboard → Core EMI → etc.) with user actions, touchpoints, emotion scores, pain points, and a live data overlay showing GA4 event counts per stage.
2. **Funnel Analysis** — 10-stage conversion funnel (Impressions → D30 Retained) with benchmark comparisons, leak detection, and revenue impact estimates. Canvas-rendered bar chart.
3. **Opportunity Backlog** — Sprint-prioritized fix list derived from funnel leaks + journey pain points, with Jira ticket copy and Claude prompt generation.
4. **Play Store Stats** — GCS-ingested install/uninstall data, traffic source breakdown, country distribution.
5. **Events Registry** — Searchable table of all GA4 events with source file references and journey mappings.
6. **CSV Importer** — Spreadsheet upload that maps rows into journey stages.

**Sidebar** has an app selector dropdown (only EMI Calculator wired today) and flow navigation (Onboarding, Dashboard, Core, Secondary, News, System). **Detail panel** slides in from the right with code references, BigQuery SQL templates, Play Store reviews, and recommended sprint fixes.

### Core Problems With This Approach

**It's a dead snapshot.** Data is baked into the HTML at generation time. No live queries, no refresh, no time-series comparison. You have to regenerate the entire file through the CLI to see updated numbers.

**One app at a time.** The app selector exists but only EMI Calculator is wired. Portfolio-level views (cross-app revenue comparison, portfolio funnel health) don't exist.

**No experiment tracking.** The opportunity backlog suggests fixes but doesn't track whether they were implemented, what happened after, or connect to the experiment lifecycle.

**No write-path interaction.** You can copy a Jira ticket or Claude prompt, but you can't trigger an ASO update, approve a Telegram action, or start an experiment from the UI.

**Terminal fatigue.** To see current state, you run CLI commands, read Telegram, check the generated HTML, and mentally stitch the picture together. The frontend should be the single pane of glass.

## Part 2: What the Interactive Frontend Should Be

### Product Positioning

**An operator cockpit for an autonomous app portfolio.** Not a generic analytics dashboard (that's what Fload tries to be). This is specifically designed for someone running the MCP-GC autonomous system — it shows what the system *did*, what it *plans to do*, what *needs human approval*, and how *experiments are performing*. The analytics views exist to contextualize the agent's actions, not as standalone reporting.

### Architecture Approach

**React SPA** served locally or deployed as a simple static site. Communicates with the MCP-GC backend through a thin REST API layer (FastAPI) that wraps the existing MCP server tool calls and SQLite queries. No new data store — reads from `store_performance.db` (extended with experiment tables) and calls MCP tools on demand.

The API layer is intentionally thin — it's a passthrough, not a new backend. Each endpoint maps 1:1 to an existing MCP tool or SQLite query. This means frontend development is decoupled from the MCP server work.

**Data flow:**

```
React SPA → FastAPI (thin wrapper) → MCP Tool calls (for live data)
                                   → SQLite queries (for experiments, action log, storefront history)
                                   → JSON file reads (for journey/events definitions)
```

### Design Language

Carry forward the current visual identity — it's already well-executed. Dark base (`#08080f`), purple accent (`#8b5cf6`), cyan secondary (`#06b6d4`), Outfit headings, Inter body, Fira Code for metrics/events. The report version established a coherent aesthetic; the interactive version should feel like the same product, just alive.

## Part 3: View-by-View Spec

### View 1: Portfolio Command Center (new — doesn't exist today)

**Purpose:** The landing page. Shows the health of every app in the portfolio at a glance, with the autonomous system's activity summary.

**Layout:** Full-width grid. Top row is a summary bar. Below is a card grid, one card per app.

**Summary bar (horizontal, full width):**
- Total portfolio MRR (sum across all apps from RevenueCat)
- Total portfolio ad revenue (trailing 30d from AdMob)
- Active experiments count (from experiments table)
- Pending approvals count (experiments awaiting Telegram confirmation)
- System trust tier badge (conservative / moderate / aggressive)
- Last PRAO cycle timestamp

**App cards (grid, 2-3 columns depending on viewport):**
Each card represents one app from `apps.json`. Shows:
- App icon + display name + package name
- Funnel health score (the 0-100 score from funnel engine, rendered as a colored ring or arc)
- Sparkline of trailing 7-day installs (from store_performance.db)
- MRR + change arrow (from RevenueCat)
- Active experiments count with status dots (green = measuring, amber = pending approval, red = rolled back)
- Worst funnel stage badge — e.g. "Store CVR 18% (↓7%)" in red if below benchmark
- Click-through to the app detail view

**Interaction:** Clicking any app card navigates to its dedicated detail view (which contains the existing journey map, funnel, etc. but now live).

### View 2: App Detail — Funnel & Diagnostics (evolution of existing Funnel Analysis)

**Purpose:** The diagnostic heartbeat for a single app. Replaces the current static funnel view with a live, interactive version.

**Layout:** Top section is the funnel visualization. Below is the diagnostic narrative. Right column (or below on narrow screens) is the experiment sidebar.

**Funnel visualization:**
Same 10-stage pipeline as today (Impressions → Store View → Install → D1 Active → Onboarding Complete → Paywall View → Trial Start → Paid Conversion → D7 Retained → D30 Retained), but rendered as a horizontal funnel with proportional bar widths. Each bar shows:
- Stage name
- User count
- Conversion rate (with color: green if above benchmark, red if below)
- Benchmark rate as a subtle reference line or ghost bar
- Leak badge on the worst stage (same red "LEAK" treatment from the current report)

**Critical difference from existing:** The funnel should allow **period comparison**. A toggle or slider that shows 7d vs 30d (already exists) but also **this week vs last week** side-by-side. The autonomous system needs to show whether its interventions are improving the funnel over time. Render both periods as overlapping semi-transparent bars so the delta is visually immediate.

**Diagnostic narrative panel (below funnel):**
This is the LLM-generated diagnostic text — the output of the Phil Carter Creation → Delivery → Capture sequencing. Instead of raw numbers, present a structured diagnosis:
- **Primary bottleneck:** "Store CVR is the biggest gap. 18% vs 25% benchmark. This is a Delivery problem — ASO metadata needs work before optimizing Capture."
- **Revenue impact:** "$489/month estimated leak"
- **Recommended action:** Links to the experiment proposal (if one exists) or a "Generate hypothesis" button that triggers the hypothesis generator

This narrative should be generated by the Coordinator agent and cached, not computed in the frontend. The API returns the latest diagnostic summary.

**Experiment sidebar:**
Compact list of all active and recent experiments for this app. Each experiment card shows:
- Type badge (ASO, Paywall, Ad Config, etc.)
- Hypothesis (one line, truncated)
- Status (proposed / approved / measuring / concluded)
- Days active / days remaining
- Current metric vs baseline (with trend arrow)
- If concluded: verdict badge (Winner / Loser / Inconclusive / Rolled Back)

Clicking an experiment opens a detail panel (see Experiment Detail view below).

### View 3: App Detail — Journey Map (evolution of existing Journey Map)

**Purpose:** Same concept as today's horizontal stage cards, but live and interactive.

**What stays the same:** Sidebar flow navigation (Onboarding, Dashboard, Core, Secondary, News, System), stage cards with user actions, touchpoints, emotion scores, live data overlay toggle showing GA4 event counts, slide-in detail panel with code references and reviews.

**What changes:**

The data overlay numbers should be **live-fetched** from the GA4 MCP when the user toggles "Live Data Overlay" on, rather than embedded in the HTML. Show a brief loading shimmer while fetching, then populate. Cache the result for the session so repeated toggles don't re-fetch.

The detail panel should include a **"Start Experiment" action** for any stage that has pain points or opportunities listed. Clicking it pre-fills an experiment spec (hypothesis from the opportunity text, metric from the stage's primary GA4 event, default 14-day observation window) and opens the experiment creation flow.

Reviews should be **live-fetched** from the Play Store MCP when the detail panel opens, not pre-baked. Show the 5 most recent reviews matching the stage's keywords.

**Add a "Heatmap" mode** — instead of showing cards, overlay a visual intensity map on the journey flow where the color intensity represents event volume. High-traffic stages glow brighter; dead-end stages (zero events) are dim. This makes it immediately obvious where users cluster and where they vanish.

### View 4: App Detail — Revenue & Monetization (evolution of existing Play Store Stats + new)

**Purpose:** Unified revenue view combining AdMob earnings, RevenueCat subscription metrics, and store performance data.

**Layout:** Three-panel layout.

**Panel 1 — Revenue streams stacked area chart:**
Time series (trailing 30 days) showing daily AdMob revenue and RevenueCat subscription revenue stacked. This is the single most important chart for a portfolio operator — "how much money did this app make today, and from what source?"

**Panel 2 — Subscription health:**
- Active subscriptions count
- MRR with month-over-month change
- Trial start rate (with benchmark comparison)
- Trial-to-paid conversion rate (with benchmark)
- Churn rate (if available from RevenueCat)
- Compact table of top offerings by subscriber count

**Panel 3 — Ad performance:**
- eCPM with 7-day trend sparkline
- Impressions, clicks, CTR
- Top ad units by revenue (from AdMob mediation report)
- Ad load failure rate (a metric already in the GA4 events — `emi_ad_load_failed` is significant at 101K events vs 93K `emi_ad_loaded`)

**Panel 4 — Store performance (replaces current Play Stats tab):**
- Installs and uninstalls time series from SQLite store_performance.db
- Traffic source breakdown (organic vs paid vs referral)
- Top countries by installs
- Store listing conversion rate trend

### View 5: Experiment Center (entirely new)

**Purpose:** The nerve center of the autonomous system. Shows all experiments across the portfolio — proposed, active, measuring, concluded.

**Layout:** Kanban-style board with columns for each status.

**Columns:**
- **Proposed** — Hypothesis generated by the system, awaiting review or approval. Each card shows the hypothesis, expected impact, and risk assessment. Actions: "Approve" (sends to Telegram approval flow or auto-approves if low-risk), "Reject" (with reason), "Edit" (modify parameters before approving).
- **Measuring** — Experiments currently running. Each card shows days elapsed, current metric vs baseline, confidence level (rendered as a progress arc toward 90%), and a mini sparkline of daily observations. Prominent "Rollback" button if something looks wrong.
- **Concluded** — Completed experiments with verdict badges. Expandable to show full before/after comparison, statistical details, and the action that was taken.
- **Rolled Back** — Experiments that were auto-reverted or manually stopped. Shows why (degradation detected, manual decision, safety trigger).

**Filters:** By app, by experiment type, by date range, by verdict.

**Aggregate stats at top:** Win rate (%), average improvement when winning, average time to significance, rollback rate. These feed the trust tier calculation.

### View 6: Action Log & Safety Monitor (entirely new)

**Purpose:** Audit trail of every autonomous action the system has taken.

**Layout:** Reverse-chronological event stream (like a terminal log, but readable).

**Each entry shows:**
- Timestamp
- App name
- Action type (icon-coded: wrench for tool call, flask for experiment, shield for safety trigger, bell for notification)
- Tool name and arguments (expandable, collapsed by default)
- Result (success / failed / blocked by policy)
- Reasoning (the LLM's explanation for why it took this action, expandable)
- Linked experiment (if applicable, clickable to experiment detail)

**Safety monitor section (top of view, always visible):**
- Current crash rate per app vs threshold (1.0%)
- Current ANR rate per app vs threshold (0.47%)
- Emergency brake status (armed / triggered / cooling down)
- Last safety scan timestamp
- Any active anomaly alerts with their triggered actions

**Filtering:** By app, by action type, by date range, by severity.

### View 7: ASO Workspace (evolution of existing Events Registry + new)

**Purpose:** Dedicated workspace for ASO experimentation — keyword tracking, listing management, and metadata A/B tests.

**Layout:** Three columns.

**Column 1 — Keyword tracker:**
Table of tracked keywords (from app rulebook `target_keywords`), showing:
- Current rank position
- Search volume estimate (from ASO MCP or AppFollow)
- Keyword difficulty score
- Rank change (↑↓) since last measurement
- Whether the keyword appears in title, short description, or full description

**Column 2 — Current listing preview:**
Renders the current title, short description, and full description as they appear on the Play Store. Highlights tracked keywords in the text with colored underlines. Shows character counts vs limits (from rulebook constraints).

**Column 3 — Experiment builder:**
Side-by-side comparison: current listing vs proposed variant. The proposed variant can be auto-generated (button triggers `generate_optimized_listing` from ASO MCP) or manually edited. Once the user is satisfied, "Start Experiment" creates an experiment spec with the listing change as the action, store CVR as the metric, and the appropriate observation window.

### View 8: Settings & Configuration (new)

**Purpose:** System configuration, not app configuration.

**Contents:**
- Connected services status (which MCP servers are configured and reachable — mirrors `get_system_status` tool output)
- Telegram bot connection status and test button
- Trust tier display with progression criteria
- PRAO cycle schedule configuration
- Safety thresholds (crash rate, ANR rate, funnel drop-off, budget cap) — editable, writes to a config file
- App rulebook viewer (read-only display of each app's YAML constraints)

## Part 4: Interaction Patterns

### Navigation
Left sidebar, always visible, with two tiers:
- **Top tier:** Portfolio Command Center, Experiment Center, Action Log (portfolio-wide views)
- **Bottom tier (app-scoped, appears after selecting an app):** Funnel & Diagnostics, Journey Map, Revenue & Monetization, ASO Workspace

Selecting an app from the Portfolio Command Center or from a persistent app-selector dropdown in the sidebar switches the bottom-tier views to that app's data.

### Data Fetching Strategy
- **Portfolio Command Center:** Fetches aggregated data on mount. Refreshes every 5 minutes if the tab is active.
- **App detail views:** Fetch data for the selected app on navigation. Cache per session. Manual "Refresh" button to re-fetch.
- **Live Data Overlay (Journey Map):** Fetches from GA4 MCP on toggle. Shows loading shimmer. Caches for 15 minutes.
- **Experiment Center:** Polls every 60 seconds for status changes (new proposals, experiments concluding).
- **Action Log:** Streams new entries via polling (every 30 seconds) or SSE if the API supports it.

### Approval Flow (in-app alternative to Telegram)
When an experiment or action needs approval, it appears in the Experiment Center's "Proposed" column AND triggers a Telegram message (existing flow). The user can approve from either surface. The API checks both — first approval wins.

### State Management
The frontend should never be the source of truth. All state lives in SQLite (experiments, actions, observations) or in the MCP servers (live metrics). The frontend reads and displays; writes go through the API which delegates to MCP tools or SQLite.

## Part 5: API Endpoints Needed

The FastAPI layer needs these endpoints (all are thin wrappers):

**Portfolio:**
- `GET /api/portfolio` — Returns all apps from apps.json with latest funnel health score and MRR
- `GET /api/portfolio/summary` — Aggregated metrics across all apps

**App detail:**
- `GET /api/apps/{package}/funnel?period=7d|30d` — Funnel data from funnel engine MCP
- `GET /api/apps/{package}/journeys` — Journey definitions from EVENTS.md / journey map data
- `GET /api/apps/{package}/events?period=7d|30d` — GA4 event counts from analytics MCP
- `GET /api/apps/{package}/revenue?period=7d|30d` — Combined AdMob + RevenueCat + GA4 revenue
- `GET /api/apps/{package}/storefront?period=30d` — Store performance from SQLite
- `GET /api/apps/{package}/reviews?stage={stage_key}` — Reviews from Play Store MCP
- `GET /api/apps/{package}/keywords` — Keyword positions from ASO MCP
- `GET /api/apps/{package}/listing/{language}` — Current listing from Play Store MCP
- `GET /api/apps/{package}/diagnostic` — Latest LLM-generated diagnostic narrative

**Experiments:**
- `GET /api/experiments?app={package}&status={status}` — List experiments
- `POST /api/experiments` — Create new experiment
- `PATCH /api/experiments/{id}` — Update status (approve, reject, rollback)
- `GET /api/experiments/{id}/observations` — Time series of observations

**Actions:**
- `GET /api/actions?app={package}&type={type}&limit=50` — Action log entries

**System:**
- `GET /api/system/status` — Connected services, trust tier, last cycle time
- `GET /api/system/safety` — Current anomaly states, crash rates, emergency brake status

## Part 6: What NOT to Build

- **User authentication.** This is a single-operator tool. Run it locally or behind a VPN. Don't waste time on login flows.
- **Real-time websockets.** Polling every 30-60 seconds is fine for this use case. The data doesn't change faster than that.
- **Mobile responsive.** This is a desktop operator cockpit. Tablet-minimum. Don't optimize for phone screens.
- **Multi-tenancy.** One instance, one operator (or small team). No org/team/permissions model.
- **Custom charting library.** Use Recharts (already available in the React artifact environment). Don't build chart components from scratch.
- **Notification system.** Telegram is the notification layer. The frontend is for when you're actively looking.

## Part 7: Open Source Positioning (if applicable)

If this ships as an open-source project, the positioning is:

**"JMIP — Journey Map Intelligence Platform"**

An open-source operator cockpit for autonomous mobile app management. Plugs into your MCP servers (Play Store, RevenueCat, GA4, AdMob, ASO) and gives you funnel diagnostics, experiment lifecycle tracking, and an action audit trail. Works with any MCP-compatible toolchain.

**Differentiator vs Fload/AppFollow/data.ai dashboards:** JMIP isn't a metrics dashboard — it's the control surface for an autonomous system. It shows you what the agent did, why, and whether it worked. The funnel diagnostic engine (Phil Carter's Subscription Value Loop + category benchmarks) is the intelligence layer. The experiment lifecycle (hypothesis → approval → measurement → verdict) is the action layer. Dashboards show you numbers; JMIP shows you what to do about them and tracks whether it worked.

### 1C. Rollback Registry

Every write operation must be wrapped in a snapshot-before / snapshot-after pattern:

```python
class RollbackManager:
    """Wraps every mutating MCP tool call with state snapshots."""

    async def execute_with_rollback(
        self,
        tool_name: str,
        tool_args: dict,
        snapshot_fn: Callable,  # function that captures current state
        rollback_fn: Callable,  # function that restores previous state
        experiment_id: str | None = None
    ) -> ToolResult:
        # 1. Capture pre-state
        before = await snapshot_fn()

        # 2. Execute the tool
        result = await execute_mcp_tool(tool_name, tool_args)

        # 3. Capture post-state
        after = await snapshot_fn()

        # 4. Store in experiments table if linked
        if experiment_id:
            update_experiment_snapshots(experiment_id, before, after)

        # 5. Log to action_log
        log_action(tool_name, tool_args, result, before, after)

        return result
```

### 3B. Experiment State Machine

```
proposed → [approval gate] → approved → [baseline measurement] → active → measuring → [evaluation] → concluded
                                                                    ↓
                                                              [degradation detected]
                                                                    ↓
                                                              rolled_back
```

**State transitions:**

| From | To | Trigger |
|---|---|---|
| `proposed` | `approved` | Telegram approval received (or `requires_approval=False` for low-risk) |
| `proposed` | `rejected` | Telegram rejection or conflict with running experiment |
| `approved` | `active` | Baseline measurement captured (7-day lookback stored) |
| `active` | `measuring` | Change deployed via MCP tool, clock starts |
| `measuring` | `concluded` | `min_observation_days` passed + statistical significance reached |
| `measuring` | `rolled_back` | Metric degraded beyond `rollback_degradation_pct` |
| `measuring` | `concluded (inconclusive)` | `max_observation_days` passed without significance |

### 3D. Statistical Evaluator

Simple but sufficient. Don't over-engineer this — you're comparing two time periods, not running a proper randomized control trial (Play Store doesn't support that for most metrics).

```python
import numpy as np
from scipy import stats

class ExperimentEvaluator:
    """Evaluates whether an experiment has reached a conclusive result."""

    def evaluate(
        self,
        baseline_values: list[float],   # daily metric values during baseline
        treatment_values: list[float],  # daily metric values during experiment
        target_improvement_pct: float,
        rollback_threshold_pct: float
    ) -> EvaluationResult:

        baseline_mean = np.mean(baseline_values)
        treatment_mean = np.mean(treatment_values)

        if baseline_mean == 0:
            return EvaluationResult(verdict="inconclusive", reason="Zero baseline")

        observed_change_pct = (treatment_mean - baseline_mean) / baseline_mean

        # Check for degradation (emergency rollback)
        if observed_change_pct < -rollback_threshold_pct:
            return EvaluationResult(
                verdict="rollback",
                confidence=1.0,
                observed_change=observed_change_pct
            )

        # Welch's t-test (unequal variance)
        t_stat, p_value = stats.ttest_ind(
            treatment_values, baseline_values, equal_var=False
        )

        confidence = 1 - p_value

        if confidence >= 0.90:  # 90% confidence threshold
            if observed_change_pct >= target_improvement_pct:
                return EvaluationResult(verdict="winner", confidence=confidence, observed_change=observed_change_pct)
            else:
                return EvaluationResult(verdict="loser", confidence=confidence, observed_change=observed_change_pct)

        return EvaluationResult(verdict="insufficient_data", confidence=confidence, observed_change=observed_change_pct)
```

**Why 90% and not 95%:** You're optimizing store listings and paywalls for a mobile app portfolio, not running a clinical trial. False positives cost you a revert; false negatives cost you weeks of missed improvement. 90% is the right trade-off for this domain.

async def run_prao_cycle():
    """The core autonomous loop. Runs once daily."""

    apps = load_app_catalog("apps.json")

    for app in apps:
        rulebook = load_rulebook(app.package_name)

        # ═══ PERCEPTION ═══
        # Consolidated fetch across all data sources
        vitals = await ask_play_store(f"Get vitals overview for {app.package_name}")
        revenue = await ask_revenuecat(f"Get MRR, trial starts, churn for last 7 days")
        analytics = await ask_analytics(f"Get DAU, retention, acquisition for last 7 days")
        ad_earnings = await ask_admob(f"Get earnings summary for last 7 days")
        funnel = await ask_funnel_engine(f"Run full funnel analysis for {app.package_name}")
        storefront = await ask_storefront_analyst(f"Latest store conversion rates")
        keyword_positions = await ask_aso(f"Check ranking for target keywords: {rulebook.target_keywords}")

        perception_state = consolidate_perception(vitals, revenue, analytics, ad_earnings, funnel, storefront, keyword_positions)

        # ═══ SAFETY CHECK ═══
        anomalies = detect_anomalies(perception_state, rulebook)
        if anomalies.critical:
            await execute_emergency_brake(app, anomalies)
            await notify_telegram(f" Emergency brake triggered for {app.display_name}: {anomalies.summary}")
            continue  # Skip reasoning/action for this app

        # ═══ REASONING ═══
        # Check active experiments — collect observations
        active_experiments = get_active_experiments(app.package_name)
        for exp in active_experiments:
            observation = measure_experiment_metric(exp, perception_state)
            store_observation(exp.id, observation)

            # Evaluate if experiment should conclude
            evaluation = evaluator.evaluate(
                baseline_values=get_baseline_values(exp.id),
                treatment_values=get_treatment_values(exp.id),
                target_improvement_pct=exp.target_improvement_pct,
                rollback_degradation_pct=exp.rollback_degradation_pct
            )

            if evaluation.verdict == "rollback":
                await rollback_experiment(exp)
                await notify_telegram(f" Auto-rolled back experiment {exp.id}: {evaluation.reason}")
            elif evaluation.verdict in ("winner", "loser", "inconclusive"):
                if exp.days_active >= exp.min_observation_days:
                    conclude_experiment(exp, evaluation)

        # ═══ HYPOTHESIS GENERATION ═══
        # Only if we have capacity for new experiments
        active_count = count_active_experiments(app.package_name)
        if active_count < rulebook.max_concurrent_experiments:
            hypothesis = await generate_hypothesis(
                app=app,
                perception_state=perception_state,
                active_experiments=active_experiments,
                rulebook=rulebook,
                trust_tier=get_current_trust_tier()
            )

            if hypothesis and hypothesis.confidence > 0.6:
                experiment = create_experiment(hypothesis)

                if experiment.requires_approval:
                    await request_telegram_approval(experiment)
                else:
                    await start_experiment(experiment)

        # ═══ ACTION ═══
        # Execute any approved experiments waiting in queue
        approved_queue = get_experiments_by_status(app.package_name, "approved")
        for exp in approved_queue:
            baseline = await capture_baseline(exp, days=exp.baseline_window_days)
            await execute_experiment(exp)  # calls the MCP tool
            transition_status(exp, "active")

        # ═══ OBSERVATION / REPORTING ═══
        daily_summary = compile_daily_summary(app, perception_state, active_experiments)
        await post_telegram_report(daily_summary)

        log_prao_cycle(app.package_name, perception_state, active_experiments)

## Key Design Decisions & Rationale

**Why SQLite (not Supabase/Postgres)?**
You're running a single-server daemon for a 15-app portfolio. SQLite handles this load trivially, has zero operational overhead, and your storefront data already lives there. When you hit 50+ apps or need multi-server, migrate.

**Why APScheduler (not Temporal/Celery)?**
Same reasoning. Three cron jobs on a single process. Temporal is for distributed orchestration across teams; you're one operator. APScheduler gives you retry, misfire handling, and timezone support in 20 lines.

**Why not Play Console's native Store Listing Experiments?**
The Google Play Developer API's experiment support is limited and often requires Play Console UI interaction. Your approach (change listing → measure store_performance.db conversion rates via GCS exports) gives you full programmatic control and works across all metadata fields.

**Why Welch's t-test (not Bayesian)?**
Bayesian A/B testing is better in theory but adds a dependency (PyMC/ArviZ) and complexity. Your experiments are before/after time series comparisons on a single variant, not concurrent A/B splits. Welch's t-test with 90% confidence is the standard for this setup. You can upgrade to Bayesian later when you're running proper holdout groups.

**Why conservative trust tier by default?**
The cost of a bad autonomous action (pushing a broken listing, overspending on UA) is much higher than the cost of waiting for Telegram approval. Let the system earn your trust with a track record before loosening the reins.
